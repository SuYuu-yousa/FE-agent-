# RAG 与向量检索

> 字节高频：RAG 流程、Rerank 作用、召回率优化、Memory vs RAG。JD 明确要求 RAG。已填好答案。

## 一、RAG 是什么、为什么用

- RAG（检索增强生成）：生成前先检索外部知识，把相关内容塞进上下文再让模型回答。
- ==一句话：先查资料，再回答，减少幻觉、增强时效和领域准确==
- 为什么不用模型直接答：大模型没有企业私有知识、时效性信息，且会「一本正经瞎编」。

## 二、RAG 工作流程 ⭐

- **离线**：采集清洗 → 分块 Chunk → Embedding 向量化 → 建索引。
- **在线**：Query 改写 → 召回 → 过滤 → Rerank → 组装上下文 → 生成 + 引用。
- ==核心链路：Chunk → Embedding → 检索 → Rerank → 生成==

## 三、Chunk 切分 ⭐

- 块大小一般 256~512 token，overlap 10%~20%（防止关键信息被切两半）。
- 策略：固定大小 / 递归分割（默认）/ 语义分割 / 结构感知（按标题、表格）。
- 进阶：**Parent-Child 父子分块**（小 chunk 精确召回、大 chunk 补上下文）。
- 坑：Chunk 太小丢上下文、太大定位不准；只改切分策略，准确率能从 62% 提到 89%。

## 四、Embedding 与向量检索

- Embedding 把文本映射成语义向量，相似文本距离近；相似度用余弦 / 内积 / 欧氏。
- 向量检索用 ANN（近似最近邻）+ HNSW 索引，平衡速度与召回。
- ==纯向量检索会漏「精确词面匹配」（专有名词、编号、SKU），所以要混合检索==

## 五、混合检索 + Rerank ⭐⭐（召回率优化核心）

### 为什么混合检索
- 稠密检索（向量）擅长语义 / 同义 / 跨语言；BM25（稀疏）擅长精确词面 / 专有名词 / 代码。
- 企业 RAG 常做 **混合检索（BM25 + Vector）**，用 RRF（Reciprocal Rank Fusion）合并排名。

### Rerank 是什么
- 召回追求「快、不漏」（Recall），用 bi-encoder，会混入「语义像但答非所问」的噪声。
- Rerank 用 cross-encoder（BGE-Reranker / Cohere）把 query+doc 拼一起精细打分，精度高一档。
- ==典型流程：召回 50 条 → Rerank 选 top-5 → 喂 LLM==

### 召回率优化系统思路
1. 先量化：Recall@K / NDCG@K + 黄金测试集。
2. Recall 低（相关文档没召回）→ 查 Chunk 是否切断语义、Embedding 领域是否匹配 → 混合检索 + Rerank。
3. Recall 高但生成差 → 噪声多 / Lost in the Middle → Rerank 精筛 + 上下文窗口扩展。
- 还有：Query 改写、多路召回、元数据过滤、Rerank 分数阈值。

## 六、Memory vs RAG ⭐（字节原题）

- **RAG**：外部知识检索（「查字典」，解决知识不足 / 过时）。
- **Memory**：对话 / 用户个性化上下文（「记笔记」，解决多轮一致性和个性化）。
- ==RAG 偏「外部知识」，Memory 偏「个性化上下文」，两者互补==

## 七、常见失败模式 + 评估

- 失败四类：**没找到、找错了、没用好、生成错了**。
- 三层评估：检索层（Recall@K / Precision@K）、生成层（Faithfulness 忠实度）、系统层（任务完成率 / 延迟 / 权限）。
- RAG 不能彻底消灭幻觉：检索错、证据不足、模型不遵循证据都会错。

## 八、加分：Agentic RAG

- 让 LLM 判断是否检索、选数据源、改写/分解查询、迭代检索并验证证据。
- 适合多跳 / 异构数据，但延迟、成本、循环风险更高。
