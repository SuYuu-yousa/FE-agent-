# 浏览器原理（渲染与运行时）

> 三条主线：页面怎么来 / 怎么显示 / 怎么更快更安全。

浏览器知识其实就三条主线：

### 1. 页面怎么来

输入 URL -> 网络 -> 响应 -> 加载资源

### 2. 页面怎么显示

解析 -> DOM/CSSOM -> Layout -> Paint -> Composite

### 3. 页面怎么更快更安全

缓存 / 调度 / 性能优化 / 安全策略



# 浏览器进程

浏览器通常至少包含浏览器主进程、渲染进程、网络相关进程或服务、GPU 进程，另外还可能有插件进程、扩展进程、音视频相关进程、存储和 utility 进程

==主进程就是管多少个标签页之类的==

==渲染进程一般每个页面一个，画这个页面==

==网络进程字面意思==

==GPU进程字面意思==

浏览器主进程负责整体协调，像标签页管理、地址栏、前进后退、窗口界面、部分权限控制、进程调度这些都归它管。

渲染进程负责某个页面的渲染工作，也就是解析 HTML/CSS、构建 DOM、样式计算、布局、绘制，以及执行页面里的 JavaScript。

GPU 进程负责图形相关加速，比如合成、光栅化等。

网络部分在现代浏览器里往往被单独抽成网络服务。



# 页面怎么来？

你现在输入了一个url

### 1.从url输入 到 准备请求

浏览器拿到 URL 后，先判断输入内容是不是一个可导航的地址(不是可能会转给搜索引擎)，再把它解析成规范化的 URL 结构，然后判断这次变化是不是一次真正的页面导航，比如只是 hash 变化就未必会重新请求；如果需要导航，它会优先检查本地状态和可复用资源，比如缓存、已有连接、已有网络信息，确认之后才进入真正的网络获取流程，也就是后面的 DNS、建连、发请求。你可以先把最开始记成一句话：==识别输入、规范 URL、判断导航、尝试复用、准备请求。==

###### q1)浏览器怎么判断你输入的是 URL 还是搜索词

浏览器先尝试按 URL 语法解析，能构成合法 URL 就直接导航，否则当搜索关键字处理。

###### q2）URL 怎么拆分，各部分是什么，标准长相

标准结构可以抽象成这一行：
`scheme://userinfo@host:port/path?query#fragment`
用一个例子：`https://user:pass@www.example.com:8080/path/to/page?name=alice&age=20#section1`，对应关系是：`https` 是协议（scheme），`user:pass` 是用户信息（一般现在很少用），`www.example.com` 是主机（host），`8080` 是端口（port，省略时 http 默认 80、https 默认 443），`/path/to/page` 是路径（path），`?` 后面 `name=alice&age=20` 是查询参数（query，服务器会收到），`#section1` 是片段标识（fragment，只在浏览器本地用，**不会**发给服务器）。浏览器内部会把这个字符串解析成一个结构化对象（类似你在 JS 里 new URL 得到的那种），后面所有流程都基于这个拆好的结构，不再拿原始字符串乱切。

### 2.发请求到返回入口文件

当浏览器已经确定“这是一个合法 URL，要导航过去”，下一步首先是做标准化和分类：比如把省略的协议补成 `https://`，把大小写无关的部分统一成规范形式，区分这次是不是只改了 hash（比如 `/#a` → `/#b`，这类叫 same-document navigation，通常不重新发请求），以及判断是当前标签页内导航还是要开新标签、新窗口。确认为“需要真正加载新文档”后，浏览器会选择或创建合适的渲染进程，并在发起网络请求之前，先尝试利用本地已有的信息：检查是否有可以直接命中的缓存、是否存在与该站点可复用的连接、是否有对应的 Service Worker 可以拦截请求；如果这些都不满足，才进入外部网络阶段，也就是基于 URL 中的 host 做 DNS 解析，基于 scheme 与端口建立或复用 TCP 连接、在 HTTPS 下完成 TLS 握手，然后构造 HTTP 请求报文发给服务器。下一步就是服务器返回响应、浏览器拿到主文档后启动“解析 + 渲染”流程，这块我们可以单独展开讲一轮。









# 服务器返回 HTML：响应头 vs 响应体

流程很简单：

1. 浏览器发请求
2. 服务器返回 HTML
3. 返回内容里分两部分理解：
   - **响应头**：先告诉浏览器“这页面该怎么处理”
   - **响应体**：真正的 HTML 内容

比如服务器会先说：

- 这个页面是什么编码
- 能不能执行外部脚本
- 能不能加载第三方资源
- 要不要缓存

然后浏览器再去解析 HTML。

# 周二补 · 渲染与缓存（填空）

## 关键渲染路径 CRP ⭐

### 完整流程
> HTML→DOM、CSS→CSSOM → 合成 RenderTree（去掉 `display:none` 等不可见节点）→ Layout 布局（算几何位置）→ Paint 绘制（画像素）→ Composite 合成（分层合并上屏）。

### 阻塞关系
> CSS 阻塞渲染（要等 CSSOM 好了才能建 RenderTree）但不阻塞 DOM 解析；JS 阻塞 DOM 解析（要执行完才继续）；JS 执行前要等它之前的 CSS 加载完（因为 JS 可能读样式）。

## 回流 Reflow vs 重绘 Repaint ⭐

### 区别
> 回流=布局变化（改宽高/增删元素/读 `offsetWidth` 等强制同步布局）；重绘=样式变化不影响布局（改颜色/背景/visibility）。==回流必触发重绘、重绘不一定回流，回流代价更大。==

### 减少回流的办法
> 批量改 class、一次改 `cssText`、`DocumentFragment` 批量插、动画用 transform/opacity（只走合成）、读写分离（避免「读-改-读」抖动）、rAF 合并。

## 合成层与 GPU 加速

### 为什么 transform/opacity 快
> 只触发 Composite 不触发 Layout/Paint，在 GPU 合成线程做（独立图层，主线程不卡）；`will-change` 提前建层；但层过多会爆显存（每层占内存）。

## 强缓存 vs 协商缓存 ⭐

> 已移至 [[🔖 网络相关 http nginx]]（HTTP 缓存节），这里不重复。

## 性能指标 LCP / FCP / CLS ⭐

### 各自含义
> FCP 首次内容绘制（第一块内容出现）；LCP 最大内容绘制（最大块出现，核心指标 <2.5s）；CLS 累积布局偏移（<0.1，稳定性）；TBT 总阻塞时长；INP 交互到下一次绘制（2024 起取代 FID 成核心指标，衡量交互响应延迟）。

## rAF vs rIC

### 区别
> `requestAnimationFrame` 每帧渲染前执行（动画/批量 DOM，60fps 即每 16.7ms）；`requestIdleCallback` 空闲时执行（低优先级：埋点、预加载）。

# 补 · 浏览器 GC 与 Web Worker ⭐（面经高频遗漏点）

## V8 垃圾回收 GC

### 为什么需要 GC
JS 自动内存管理，不用手动 free；不回收就内存泄漏。

### V8 分代回收
- 新生代（Young）：Scavenge 复制算法，空间小、回收频繁、对象存活短。
- 老生代（Old）：标记-清除（Mark-Sweep）+ 标记-整理（Mark-Compact），空间大、回收慢。
- ==核心思想：大部分对象朝生夕死，年轻对象放新生代快速回收，活下来的晋升老生代==

### 标记-清除（Mark-Sweep）
从「根」（全局对象、当前执行栈）出发，标记所有可达对象，清除未标记的；会产生内存碎片，所以配合标记-整理（移动存活对象、压缩空间）。

### 引用计数（老方案，为何被弃）
引用数归零就回收，但**循环引用**（A 引用 B、B 引用 A）永远不为零 → 泄漏。V8 主要用标记清除，不靠引用计数。

### 常见内存泄漏场景 ⭐
- 全局变量挂大对象；未清理的定时器 / 事件监听器；闭包常驻引用；游离的 DOM 引用。
- 排查：DevTools Memory 拍堆快照对比、Performance 观察内存曲线。

### 结合 Agent
AI 长会话：消息列表、流式 chunk、定时器、未关闭的 EventSource/WebSocket，都容易积累内存——长会话要做「滑动窗口裁剪」+「及时清理监听」。

## Web Worker ⭐

### 为什么有它
JS 主线程单线程，CPU 密集计算（大 JSON 解析、编解码、大量计算）会阻塞 UI 渲染导致掉帧。

### 通信模型
- `new Worker()` + `postMessage` / `onmessage`，消息用**结构化克隆**传递（大对象有拷贝开销，可用 Transferable 转移所有权）。
- 不能操作 DOM、不能直接用主线程全局变量，靠消息通信。
- 与页面间通信同机制，完整对比见 [[跨端 跨页面通讯]]。

### 三种类型
- **Dedicated Worker**：一个页面专属，最常用。
- **Shared Worker**：同源多页面共享。
- **Service Worker**：独立于页面，做缓存/PWA/离线（常与 PWA 一起考）。

### 结合 Agent ⭐
- AI 流式输出的 markdown 解析、token 预处理、重计算放 Worker，避免打字机卡顿。
- 多标签页 / 多会话共享状态可上 Shared Worker；离线缓存模型输出用 Service Worker。
